## ExCoT: Optimizing Reasoning for Text-to-SQL with Execution Feedback

### Abstract 
- **Context of paper** : Text-to-SQL demands precise reasoning to convert natural language questions into structured queries. While large language models (LLMs) excel in many reasoning tasks, their ability to leverage Chain-of-Thought (CoT) reasoning for text-to-SQL remains underexplored. We identify critical limitations: zero-shot CoT of- fers minimal gains, and Direct Preference Optimization (DPO) applied without CoT yields marginal improvements.
- **Task/Objective** : We propose ExCoT, a novel framework that **iteratively optimizes open-source LLMs by combining CoT reasoning with off-policy and on-policy DPO**, relying solely on execution accuracy as feedback. This approach eliminates the need for reward models or human-annotated preferences.
- **Findings** : Our ex- perimental results demonstrate significant performance gains: ExCoT improves execution accuracy on BIRD dev set from 57.37% to 68.51% and on Spider test set from 78.81% to 86.59% for LLaMA-3 70B, with Qwen-2.5- Coder demonstrating similar improvements. Our best model achieves state-of-the-art per- formance in the single-model setting on both BIRD and Spider datasets, notably achieving 68.53% on the BIRD test set.1


### Steps for implementation
#### 1. Generate CoT Data using GPT-4o (External Model) [ Can be improvised to GPT 5 ]
- This stage builds the training dataset used for SFT & DPO. [SFT - Supervised Fine Tuning, DPO - Direct Preference Optimization]
##### Steps in Training
- Step 1 : You take each question & database schema.
- Step 2 : You prompt GPT-4o with a reasoning prompt (CoT), asking it to show steps + final SQL.
- Step 3 : GPT-4o generates up to 32 SQL candidate queries (short CoT + complex CoT versions).
- Step 4 : For every generated SQL:
    - Step 4.1 : Extract only the last SQL block.
    - Step 4.2 : Execute it on SQLite.
    - Step 4.3 : Compare the output with ground truth SQL results.
##### You get two datasets:
- 1. Correct Solutions → Win examples
- 2. Wrong Solutions → Lose examples
 
     
#### 2. SFT (Supervised Fine-Tuning) 
- Now you fine-tune your base LLM [Llama / Bloom / Gamma / Mistral ... ]
- IMP: **Only the correct GPT-4o SQL[improvised to GPT5] + CoT reasoning traces**
- This teaches the model:
1. proper SQL structures
2. proper reasoning patterns
3. schema linking
4. join construction
5. aggregation patterns
SFT mostly warms up the model but gives limited performance.

#### 3. Off-Policy DPO [DPO - Direct Preference Optimization]
- [Off Policy - Training the model using the data generated by external model]
- Now the model learns preferences using correct vs. incorrect samples.
##### How does it works ?
- Step 1 : For every question, you take the GPT-4o generated:
    - Step 1.1 : Win (correct SQL)
    - Step 1.2 : Lose (wrong SQL)
- Step 2 : **You create preference pairs** (Win > Lose).
- Step 3 : DPO trains the model to prefer the correct reasoning & SQL.
- Step 4 : Pairs with maximum edit-distance are chosen (furthest curriculum), so the model learns strong corrections.
##### Why does it works ?
- DPO teaches the model:
- 1. “Prefer SQL that executes correctly”
- 2. “Avoid SQL that fails / returns wrong output”
     
#### 4. On-Policy Iterative DPO (MOST IMPORTANT PART)
- [On Policy - Training model using the data generated by own model] 
- This is the key novelty
##### Steps to perform(self improvement loop)
1. You again generate 32 candidates per query.
2. Execute all candidate SQLs on SQLite.
3. Mark correct (win) / incorrect (lose).
4. Perform another round of DPO — this time with the model's own data.
##### Why improve the accuracy ?
1. The model fixes its own mistakes.
2. Improves its own SQL patterns.
3. Produces longer, more accurate CoT over time.
4. Moves from “semi-correct patterns” to “fully correct templates”.
- After performing 2-3 loops, the accuracy will improve heavily.


### My Novality to the Work
##### Reason for most of the error occur in EXCOT
1. Wrong JOIN conditions — joins on unrelated columns or missing join paths.
2. Incorrect table selection — irrelevant tables included or correct ones omitted.
3. Invalid aggregation grouping — because the model doesn’t track dependencies.
4. Nested query failure — model can’t reason over multi-hop relations (A→B→C).

##### Graph based Schema Encoding in EXCOT
- You represent the database schema as a graph, not as text.[Each node = table / column, Each edge = relationship (foreign key, primary key, reference)]
##### You can build three graphs:
1. Foreign Key Graph → shows table relationships (who links to who)
2. Relation Graph → high-level structure of joins
3. Join Graph → path of possible joins between tables
##### embed this graph using:
- RAT-SQL encoder (Relation-Aware Transformer)
- Graph Neural Network (GNN) — [e.g. Graph Attention Network (GAT)]
These embeddings are then passed into the LLM input before query generation.
##### Why it fixes ExCoT’s main issue:
1. The model understands relational structure explicitly before reasoning.
2. CoT reasoning steps become schema-aware (“JOIN A and B because foreign key X connects them”).
3. DPO training now gets clearer feedback signals — when SQL fails, the model can trace which relation caused the mismatch.
4. Especially improves multi-table and nested queries, where ExCoT struggles most.
- We should integrate Graph-Based Schema Encoding before the LLM input during Stage 2 (Supervised Fine-Tuning).
The encoder transforms relational schemas into graph embeddings that make the model’s reasoning schema-aware.
During DPO (Stage 3), these embeddings continue to guide reasoning but are not retrained.
